# Fable Image Tracking

8th Wall / Zappar のような **image tracking（自然特徴点ベースの画像トラッキング WebAR）** を、OpenCV.js などの CV ライブラリを一切使わずスクラッチで実装した TypeScript プロジェクトです。カメラでトラッキングターゲット（画像）を映すと、コンテンツ（画像・動画・3D）がターゲットに張り付いて表示されます。

外部依存はレンダリング用の **Three.js のみ**。トラッキングは全て自前実装です（WASM カーネルは AssemblyScript 製）。

## デモの動かし方

```bash
npm install
npm run dev   # WASMビルド後、--host 付き自己署名HTTPSで起動
```

1. `target.html`（アプリ内リンク「サンプルターゲットを別画面で開く」）を別のディスプレイ・スマホで表示するか印刷する
2. アプリ（`index.html`）で「カメラを起動してはじめる」を押す
3. カメラでターゲットを映すと、コンテンツが画像に張り付く

- **コンテンツ切替**（HUD セレクタ）: 画像（サンプル・デフォルト）/ 動画（サンプル同梱、H.264 MP4 + VP9 WebM を `canPlayType` で自動選択）/ 3D キューブ
- **判定を表示**（デフォルト OFF）: 緑の枠＝推定ホモグラフィ、半透明プレーン＋3 軸＝6DoF ポーズ、黄点＝追跡中の特徴点、というデバッグ可視化をまとめて ON/OFF
- **カスタムターゲット**: スタート画面のファイル選択から任意の画像をターゲットにできます（模様が複雑で非対称な画像ほど安定）

> **Note:** getUserMedia は secure context が必要なため、開発サーバは [`@vitejs/plugin-basic-ssl`](https://github.com/vitejs/vite-plugin-basic-ssl) による自己署名 HTTPS で起動します（`https://<PCのIP>:5173` にスマホからアクセスし、証明書警告は「詳細設定 → アクセスする」で進む）。

## アーキテクチャ全体像

8th Wall / Vuforia / MindAR と同じ古典的な **detect → track** の 2 段構成を、**Web Worker + WASM** で描画（60fps）と処理を分離して実行します。

```
[オフライン] ターゲットコンパイル（Worker 内、@zappar/imagetraining に相当）
  参照画像 → スケールピラミッド(5段, 1/√2) → FAST-9 コーナー検出 → 向き推定
          → rBRIEF(ORB) 記述子 → マルチスケール特徴点バンク（~800点）
          → 密アライメント用テンプレート（勾配・ヤコビアン・ヘッシアン逆行列を事前計算）

[Worker / WASM] フレーム処理（縮小グレースケールを Transferable で往復）
  ├─ SEARCHING: FAST + ORB → ハミング距離マッチング(cross-check + ratio test)
  │             → RANSAC ホモグラフィ → 妥当性検査 → NCC 検証 → TRACKING へ
  └─ TRACKING:  ピラミッド Lucas-Kanade（等速運動予測でウォームスタート）
                → forward-backward チェック → 事前値ゲート付き決定論的フィット
                → 密なサブピクセル精密化（逆合成 Gauss-Newton、~0.4ms）
                → フォトメトリック検証（NCC）で見た目の整合を毎フレーム確認
                → 特徴点が枯渇したら密アライメントだけで追跡継続（後退・遠距離対応）
                → 破綻したら同一フレーム内で即再検出
  → H を分解して 6DoF ポーズ (H = K [r1 r2 t])、焦点距離をオンライン自己校正
  → ポーズ・コーナー四辺形をキャプチャ時刻付きで返送

[メインスレッド] フレーム同期表示（商用エンジンと同方式）
  → キャプチャした各フレームをフル解像度でバッファし、その結果が届いた瞬間に
    「処理したフレーム」と「そのフレームで計測したコーナー」を同じペイントで表示
  → 予測誤差が「ズレ」として見える構造自体が存在しない（遅延はカメラ映像側に
    ~1 処理周期として乗る。カメラセンサーは元々 30fps なので体感は同等）
  → 単発ロストは 300ms までコースティング（ちらつき防止）
  → 平面コンテンツ（画像/動画）: ホモグラフィから CSS matrix3d で直接ワープ
  → 3D コンテンツ（キューブ）: Three.js（自己校正済み焦点距離と一致した射影）
```

### 張り付き精度のための設計ポイント

- **フレーム同期表示**: カメラ映像はライブ `<video>` ではなく、トラッカーが処理を終えたフレームをキャンバスに描画して表示します。オーバーレイとカメラ画素が常に同一時刻のものになるため、追跡遅延や予測誤差がマーカーとのズレとして見えません（8th Wall / Zappar が張り付いて見える最大の理由）
- **平面コンテンツはポーズを経由しない**: 画像・動画はターゲット平面上にあるので、焦点距離の仮定誤差を含む 3D ポーズ分解を使わず、計測したホモグラフィそのもので CSS matrix3d 合成します。張り付き精度＝トラッカーの計測精度になります
- **密なサブピクセル精密化**: 特徴点ベースの H は個々のコーナーの LK ノイズを含むため、参照テクスチャ全体（132px テンプレート上の高勾配 ~1400 点）を逆合成 Gauss-Newton で直接位置合わせして締め上げます。合成 E2E で最悪コーナー誤差 4px → **1.5px 未満**
- **決定論的な追跡時フィット**: 追跡中は RANSAC のランダム性を排除（運動予測を事前値にゲーティング + 反復最小二乗）。静止シーンでのフレーム間コーナー変動は 0.05px 未満
- **密アライメントレスキュー**: カメラを引いてターゲットが小さくなると FAST コーナーが先に枯渇しますが、コーナー不要の密アライメントで追跡を継続（画面上 ~50px まで）。毎フレーム NCC 検証付きなので当てずっぽうの継続表示ではありません
- **コースティング**: モーションブラー等による 1〜数フレームの単発ロストでは表示を消さず、最終計測から 300ms まで外挿で継続（ちらつき防止）。再捕捉時の補正は One-Euro の連続性が吸収
- **焦点距離の自己校正**: `K⁻¹H` の列直交性の破れを毎フレーム評価し山登りで焦点距離を推定（正面ビューは情報がないのでゲート）。3D コンテンツの精度が使うほど向上
- **レンズ歪みの自己校正（Brown k1）**: ジオメトリは理想（無歪み）座標系で扱い、観測は入口で undistort・出力コーナーは出口で distort。k1 は密アライメント残差を最小化する値をフォトメトリックに山登り推定（ターゲットが画面周辺に届いた時のみ更新）。画面端での張り付き精度が向上
- **Huber ロバスト密アライメント**: 残差を MAD スケールの Huber 重みで毎反復リウェイト（IRLS）。部分遮蔽（ターゲットに手がかかる等）や鏡面反射が推定を引っ張らない（25% 遮蔽でコーナー誤差 1px 未満）
- **IMU（ジャイロ）フュージョン**: `devicemotion` の角速度をフレーム間で積分し、`K·R(ωΔt)ᵀ·K⁻¹` の回転ホモグラフィとして Worker へ供給。等速予測の回転成分を実測で置換するので、モーションブラーで画像が使えない瞬間も事前値が正確（突発的な高速回転でも追跡維持）。iOS は開始ボタンのジェスチャ内で権限要求、非対応環境では自動オフ

## Web Worker + WASM

- CV カーネル（リサイズ / FAST / ORB 記述子 / ハミングマッチング / LK オプティカルフロー）は **AssemblyScript**（`assembly/index.ts`）で WASM 化。純 TS 実装（`src/core/`）と数値的に一致することをパリティテストで保証し（ピラミッドはバイト一致）、WASM が使えない環境では自動で TS 実装にフォールバック
- Node ベンチマーク（360x270）: 検出+記述子 33.7ms → **16.2ms**、LK 追跡（80 点 × 往復）7.5ms → **3.4ms**（約 2.1 倍）。実機 iPhone で処理 55〜60fps
- Worker とは in-flight 1 フレームの Transferable バッファ往復。カメラ＋コンテンツは処理レート（~30fps、センサーと同等）でフレーム同期表示、3D レンダリング自体は 60fps
- ビルド: `npm run asbuild`（`asc` は純 JS コンパイラ、ネイティブツールチェーン不要）が `public/tracker.wasm`（~9KB）を生成。dev / build / test スクリプトが自動実行

## 実装したアルゴリズム（すべてスクラッチ）

| モジュール | 内容 |
| --- | --- |
| `src/core/fast.ts` | FAST-9/16 コーナー検出（高速棄却・NMS・サブピクセル補間・グリッド分散選択）、intensity centroid による向き推定 |
| `src/core/orb.ts` | 回転補正付き BRIEF（ORB 相当）。固定シード乱数による 256 ペアのテストパターン、積分画像による 5x5 ボックス平滑化、popcount ハミング距離 |
| `src/core/matcher.ts` | 総当たりハミングマッチング + Lowe ratio test + cross-check |
| `src/core/homography.ts` | 正規化 DLT（Hartley 正規化 + 8x8 正規方程式をガウス消去で解く） |
| `src/core/ransac.ts` | 適応的反復回数の RANSAC、退化サンプル除去、インライアでの再フィット |
| `src/core/opticalflow.ts` | ピラミッド Lucas-Kanade（Bouguet 方式、運動予測ウォームスタート対応） |
| `src/core/densealign.ts` | 逆合成 Gauss-Newton による密なホモグラフィ精密化（サブピクセル、ゲイン/バイアス照明不変） |
| `src/core/pose.ts` | ホモグラフィ分解による 6DoF ポーズ復元、直交性欠損による焦点距離自己校正 |
| `src/core/filter.ts` | One-Euro フィルタ |
| `src/core/predictor.ts` | クォータニオン演算 + 等速外挿によるポーズ予測（表示時刻への補間） |
| `src/core/quadfilter.ts` | コーナー四辺形の外挿 + One-Euro 平滑化（平面コンテンツの 60fps ピン留め） |
| `src/core/imageops.ts` | グレースケール変換、バイリニアリサイズ、積分画像、スケールピラミッド |
| `src/core/kernels.ts` | CV カーネルの抽象化（TS 実装 = WASM のリファレンス） |
| `assembly/index.ts` | AssemblyScript 製 WASM カーネル（TS 実装と数値一致） |
| `src/wasm/engine.ts` | WASM メモリレイアウト管理とカーネルラッパー |
| `src/tracker/target.ts` | ターゲットコンパイル（マルチスケール特徴点バンク生成） |
| `src/tracker/tracker.ts` | detect/track ステートマシン、FB チェック、決定論的フィット、密精密化・レスキュー、NCC 検証、焦点距離校正 |
| `src/tracker/worker.ts` | トラッキング Worker（WASM カーネル優先、TS フォールバック） |
| `src/render/renderer.ts` | Three.js オーバーレイ + CSS matrix3d 平面合成、cover-fit レイアウト、速度適応ポーズ平滑化 |

## 特徴点について（FAST + ORB を選んだ理由）

特徴点は **FAST-9 コーナー + ORB 系バイナリ記述子**という古典 CV の定番構成です。SIFT のような「最高精度」系ではありませんが、リアルタイム WebAR にはこの系統が事実上の標準です（MindAR も同系統。ORB-SLAM が実証したように、リアルタイム性が必要な場面では ORB 系が最有力）。

- **FAST-9**: 検出が圧倒的に速い（16 画素の円弧比較のみ）。サブピクセル補間・グリッド分散選択・マルチスケールピラミッドで弱点（精度・スケール不変性の欠如）を補強
- **rBRIEF (ORB)**: 256bit バイナリ記述子。ハミング距離＝popcount 1 命令で照合でき、回転不変（intensity centroid で向き推定）、ゲイン/バイアス照明変化に頑健
- 本家 ORB は機械学習で選別したテストペア配置を使いますが、本実装は固定シード乱数生成（分散最大化の学習なし）なので識別力はやや劣ります。ただし本プロジェクトでは**特徴点は初期検出とラフな追跡だけを担い、最終精度は密アライメントが出す**設計なので、ここがボトルネックにはなりにくいです

さらに上を狙う選択肢: 本家 ORB の学習済みパターン移植（低コスト・効果小）、AKAZE 系（高精度・重い）、SuperPoint 等の学習ベース特徴（最高性能・ONNX/WebGPU 推論が必要）。商用 SDK（Zappar 等）は独自学習の特徴量を使っていると推測されます。

## テスト

```bash
npm test        # vitest 48テスト（pretest で WASM を自動ビルド）
npm run typecheck
```

- **単体テスト**: コーナー検出、既知ホモグラフィ復元、40% 外れ値下の RANSAC、オプティカルフロー（ウォームスタート含む）、ポーズ復元、焦点距離欠損関数、密アライメント収束（摂動 2px 超→0.4px、照明不変）、外挿フィルタ
- **WASM パリティ**: 全カーネルで TS 実装と数値一致（ピラミッドはバイト一致）
- **E2E（合成フレーム）**: 検出→追跡でコーナー誤差 1.5px 未満、静止シーンでフレーム間変動 0.05px 未満、20px/フレームの高速運動、画面上 48px までの後退追跡
- **ブラウザスモークテスト**: Chromium のフェイクカメラ（y4m）にサンプルターゲットを流し込み、Worker + WASM 経由でトラッキング到達、画像/動画コンテンツの合成まで自動検証

## チューニングポイント

- `PROC_WIDTH`（`src/main.ts`）: 処理解像度（既定 360px）。上げると精度・ロバスト性が上がり、fps が下がる
- `fastThreshold` / `maxFrameFeatures`（`ImageTracker` オプション）: 特徴点の量と質
- `ransacThreshold`: インライア判定の厳しさ（処理解像度ピクセル）
- `minDetectNCC` / `minTrackNCC`: フォトメトリック検証の厳しさ（誤検出耐性 ⇔ ブラー耐性）
- `QuadFilter` の `minCutoff` / `beta`: 平面コンテンツの応答性 ⇔ 静止時の安定性
- `defaultIntrinsics`: 焦点距離の初期値（水平 FOV ~64° 仮定。自己校正が使用中に補正）

## 制限と今後の拡張

- **単一ターゲット**: 複数ターゲット対応はバンクを分けてマッチングを分岐すれば可能
- **遠距離からの初回検出**: 記述子パッチ（31px）の制約で、検出はターゲットがある程度の大きさで映っている必要があります（一度捕捉すれば密アライメントで ~50px まで追跡継続）
- **WASM SIMD**: 現状はスカラー WASM。`i8x16.popcnt` 等の v128 化でさらに高速化余地あり
- **ローリングシャッター補正**: 速いパン中の CMOS 行順次読み出し歪みは未補正（運動予測ベースの行時刻補正で対応可能）
- 強い鏡面反射・激しいモーションブラーには弱い（コースティングで見た目は橋渡し）
